# Jamba (AI21 Labs)

**Detection note.** Three distinct shapes appear in code: hosted API IDs (`jamba-large`, `jamba-mini`, or dated `jamba-mini-2-2026-01`), HuggingFace repos (`ai21labs/AI21-Jamba-*`), and Bedrock IDs (`ai21.jamba-1-5-large-v1:0`). A Maestro integration (`/studio/v1/maestro/runs`) is a *different* architecture from a Jamba chat integration and should be classified separately.

### API surface

- Chat completions at `https://api.ai21.com/studio/v1/chat/completions`. Body: `model` (`jamba-large` or `jamba-mini`), `messages`, `tools`, `documents`, `response_format`, `max_tokens` (**≤ 4096**), `temperature` (0.0–2.0, default 0.4), `top_p` (default 1.0), `stop`, `n` (1–16, default 1), `stream`.
- Documented parameter interactions: **`stream` "is incompatible with tools and requires `n=1`"**, and "If `n > 1`, setting `temperature = 0` will fail." A streaming agent loop and tool calling are mutually exclusive on this API.
- The shape is OpenAI-*like* (`messages`, `tools[].function`, `tool_calls`, `response_format`, `role: "tool"` with `tool_call_id`, `finish_reason`, `usage.*`), **but no AI21-owned page claims OpenAI compatibility or OpenAI-SDK support — that claim is not publicly documented as of 2026-09-08.** Self-hosting under vLLM does yield an OpenAI-compatible server, but that is vLLM's property, not AI21's API.
- **For agentic work AI21 points at Maestro, not the Jamba chat API.** `POST https://api.ai21.com/studio/v1/maestro/runs` takes `input`, a **required** `system_prompt`, `requirements` (up to 10 named conditions with `name`, `description`, `is_mandatory`), `tools`, `models`, `budget` (`"low"`/`"medium"`/`"high"`, default low), `include` (`"data_sources"`, `"requirements_result"`), and `response_language`. Maestro routes to first-party `jamba-large`/`jamba-mini` **and to third-party models** (Claude, GPT, Gemini, Llama, Mistral, Qwen IDs).
- **Architecturally this split is the main finding: tools, MCP, requirement validation and budget control live in Maestro, one abstraction layer above the Jamba chat API.** An agent built directly on Jamba chat has none of them and must supply its own loop.

### Reasoning state

- **There is no reasoning or thinking mode on the Jamba API.** The response schema has no reasoning field, `finish_reason` is only `"stop"` or `"length"`, and the request has no reasoning parameter. AI21's prompt-engineering page offers only ordinary prompted chain-of-thought: "you can increase the accuracy by asking the LLM to explain each step it takes in the process."
- **Reasoning exists in the family only as a separate open-weights model — Jamba Reasoning 3B** (`ai21labs/AI21-Jamba-Reasoning-3B`, Apache 2.0, 256K context, trained with "online reinforcement learning with RLVR") — **which is not exposed on the API** (the foundation-models table lists Jamba 3B's API endpoint as N/A).
- Consequently **replaying reasoning state across turns is a non-question for the hosted API** — there is no state to replay, and no thought-signature or encrypted-content mechanic to get wrong.
- Maestro's `budget` (`low`/`medium`/`high`) is the nearest analogue to a reasoning-effort dial, but AI21 does not describe it as reasoning-token control; do not treat it as one in a cost model.
- **Gap:** whether Jamba Reasoning 3B emits or requires `<think>`-style blocks, or a thinking toggle in its chat template, is **not publicly documented as of 2026-09-08**.

### Tool semantics

- OpenAI-shaped definitions: `{"type": "function", "function": {"name", "description", "parameters"}}`. "Function calling is available for all Jamba models via the Chat Completions API."
- **"Functions must be described by the user in the request; there are no built-in functions"** — no server-side code interpreter, no web search, no hosted retrieval at the Jamba layer. Every tool is client-side and every execution is yours.
- Responses carry `tool_calls[]` with `id`, `type: "function"` (currently the only value), and `function.name` / `function.arguments`; results return as `role: "tool"` messages with a matching `tool_call_id`.
- **Confirmed limitation: streaming is incompatible with tools.** A tool-using Jamba agent cannot stream.
- **MCP is a Maestro capability, not a Jamba chat capability:** "When you define an MCP tool in the `tools` parameter, AI21 Maestro acts as an MCP client." Fields: `type: "mcp"`, `server_label`, `server_url`, optional `headers` and `allowed_tools`; auth via bearer token, custom-header API key, or OAuth. **Hard constraint: "AI21 Maestro supports only remote MCP servers, not local ones."**
- **Self-hosted parser dependency is real and version-split.** Serving Jamba 1.6 under vLLM requires `--enable-auto-tool-choice --tool-call-parser jamba` (alongside `--quantization="experts_int8" --tensor-parallel-size=8`); **without the parser, tool calls will not parse.** Jamba Reasoning 3B uses a **different** parser — `--enable-auto-tool-choice --tool-call-parser hermes`, on vLLM ≥ 0.11.0 with `--mamba-ssm-cache-dtype float32`. A deployment serving both must configure them separately.
- **Gap:** `tool_choice` options, parallel tool-call support, and any tool-count cap are **not publicly documented as of 2026-09-08**.

### Modality support

- **Text only.** The chat request documents `messages` and `documents` (text with metadata); there are no image, audio, or video content types in the request or response schemas. No speech, realtime/voice, or generated-media models exist in the family.
- **AI21 never affirmatively states "text-only"** — this is inferred from complete request/response schemas, and a positive statement of modality scope is **not publicly documented as of 2026-09-08**. Treat any multimodal Jamba claim from a third party as unverified.

### Context behavior

- **256K across Jamba Large 1.7, Jamba Mini 2, and Jamba 3B.** AI21 claims "the longest context window (256K tokens) among open models" and an "effective context length of 256K tokens."
- **The documented degradation lands 25× earlier than the window:** "When asking the model to process or rewrite very long documents (above 10k tokens), don't submit them in a single pass. The model is likely to compress, summarize, or truncate the content." **AI21's own guidance is to chunk above roughly 10K tokens for transformation work.**
- **`max_tokens` is capped at 4,096** ("Maximum 4096 tokens for Jamba models"). Against a 256K input window that is a 64:1 asymmetry, and it is the single most consequential runtime constraint for agentic use: long plans, large diffs, and bulk structured extraction do not fit in one response. **Design for chunked, multi-call output from the start.**
- Self-hosted, the practical context is lower than nominal: the Jamba Large 1.7 card notes context "220K tokens long on 8 80GB GPUs" with ExpertsInt8 quantization.
- **Gaps:** prompt caching is **not publicly documented as of 2026-09-08** (no caching field in the chat request, no caching page in the docs), and neither are overflow/truncation semantics.

### Structured output path

- **JSON mode only:** `response_format` set to `{"type": "json_object"}`.
- **The schema lives in the prompt, not in the API call.** AI21: "Use the `response_format=json` API parameter and specify the expected structure in the prompt itself." There is no strict JSON-schema enforcement, no grammar parameter, and no `json_schema` variant. **Structural correctness is guaranteed only to the level of "is valid JSON"** — field names, types, and required fields are not enforced.
- Any system depending on schema conformance must validate downstream and retry; this is not a constrained-decoding family.
- The nearest thing to schema enforcement in the AI21 stack is **Maestro's `requirements` array** (up to 10 named conditions with `is_mandatory`), which is validation-by-checking after generation, not constrained decoding during it.

### Deployment & residency

- Jamba's differentiator is that it ships as open weights and self-deploys. **But every third-party platform lags AI21's own SaaS, some by two generations:** AI21 SaaS at 2, HuggingFace at 2, Kaggle at 1.7, GCP Model Garden at 1.6, Microsoft Azure at 1.5, AWS SageMaker at 1.5, AWS Bedrock at 1.5.
- Self-hosting: vLLM "version `v0.6.5` to `v0.8.5.post1`" for Jamba 1.6 (Docker `vllm/vllm-openai:v0.8.5.post1`), `--tensor-parallel-size=8`. Hardware: Jamba Mini ≈ 96.07 GB (~55 GB quantized), Jamba Large ≈ 743 GB (~400 GB quantized). Note the self-deployment guide documents 1.6 model IDs while the API is at 1.7/2 — **the self-host docs trail the hosted models.**
- **Licensing splits by model and is easy to get wrong.** Jamba Large 1.7 is under the **Jamba Open Model License** ("a permissive license allowing full research use and commercial use under the license terms"); **Jamba2 (3B and Mini) and Jamba Reasoning 3B are Apache 2.0**. A blanket "Jamba is Apache 2.0" claim is false for the Large line — check the specific repo before shipping.
- **On Bedrock, Jamba is Legacy and stranded:** `ai21.jamba-1-5-large-v1:0` and `ai21.jamba-1-5-mini-v1:0`, us-east-1 only, Legacy 2026-05-26, **EOL 2026-11-26**, with higher-priced public extended access already begun 2026-08-26. **Bedrock never carried 1.6 or 1.7, so there is no in-place upgrade — the only forward path is off-platform, to AI21 SaaS or self-hosting.** Treat a Bedrock Jamba integration as a migration project, not a version bump.
- **AI21's data-retention and training-use posture for customer prompts is not publicly documented as of 2026-09-08.** `docs.ai21.com/docs/training-data-1` covers pretraining corpus composition only. No VPC, on-prem, or air-gapped deployment claim appeared on any AI21-owned page reached. For a residency-constrained deployment, **self-hosting is the only posture this family can actually evidence.**

### Known production failure modes

- **A design that assumes output can be as large as input.** The 4,096-token ceiling against a 256K window breaks long plans, large diffs, and bulk extraction; the failure is a truncated response with `finish_reason: "length"`, not an error.
- **Long-document rewriting in a single pass**, which AI21 warns will be compressed, summarized, or truncated above ~10K tokens.
- **A streaming tool-using agent**, which the API forbids (`stream` is incompatible with `tools`).
- **JSON mode trusted as schema enforcement.** Valid JSON is guaranteed; the schema is not. Any consumer that indexes into expected fields needs validation and a retry path.
- **Self-hosting without the right parser.** `--tool-call-parser jamba` for Jamba 1.6 and `--tool-call-parser hermes` for Jamba Reasoning 3B — tool calls silently fail to parse without them, and the two are not interchangeable.
- **A blanket Apache-2.0 assumption** applied to Jamba Large 1.7, which is under a different license.
- **A Bedrock Jamba deployment treated as upgradeable in place.** It is EOL 2026-11-26, already in higher-priced extended access, and Bedrock never carried 1.6 or 1.7.
- **A moving alias in production.** `jamba-mini` now resolves to a 2 (2026-01) snapshot while `jamba-large` still resolves to a 1.7 (2025-07) one — the same alias convention means different generations for the two models.
- **A residency or retention claim about AI21's hosted API**, which AI21 does not document.
- **Maestro's `budget` treated as a reasoning-effort dial** in a cost model, which AI21 does not support.

### Harness requirements

- **Design output in chunks.** Assume a 4,096-token ceiling per call and build multi-call assembly rather than one large response.
- Chunk documents above roughly 10K tokens for transformation tasks, per AI21's own guidance.
- Choose one of streaming *or* tools — the API will not give you both.
- Validate every structured response against the intended schema and implement a retry path; JSON mode does not enforce shape.
- **Pin dated snapshot IDs** (`jamba-large-1.7-2025-07`, `jamba-mini-2-2026-01`), as AI21 itself advises, rather than the moving aliases.
- When self-hosting, set the model-specific tool-call parser explicitly and verify tool calls actually parse before shipping.
- Check the license on the specific repo, not the family.
- If the agent loop needs hosted tools, MCP, or requirement validation, that is a **Maestro** decision — evaluate Maestro as a harness in its own right, including that it routes to third-party models and that MCP servers must be remote.
- For a residency obligation, plan on self-hosting; AI21 publishes no retention or residency posture for its API.

### Version-specific notes

- **Jamba Large 1.7** — `jamba-large` / `jamba-large-1.7-2025-07`, 398B total / 94B active, 256K context, 4,096 max output. Under the **Jamba Open Model License**, not Apache 2.0. **There is no Jamba Large 2 on the API as of 2026-09-08.** Cost tier: $$$.
- **Jamba Mini 2** — `jamba-mini` / `jamba-mini-2-2026-01`, 52B total / 12B active, 256K context, 4,096 max output, **Apache 2.0**. Cost tier: $$.
- **Jamba 3B** — 256K context, **no API endpoint**; weights only. Cost tier: $ (self-hosted).
- **Jamba Reasoning 3B** — `ai21labs/AI21-Jamba-Reasoning-3B`, Apache 2.0, 256K context, RLVR-trained. **Not on the API.** Requires the `hermes` tool-call parser and vLLM ≥ 0.11.0 with `--mamba-ssm-cache-dtype float32`. Cost tier: $ (self-hosted).
- **Maestro** — an agent platform, not a model. Required `system_prompt`, up to 10 `requirements`, a `budget` dial, remote-only MCP, and routing to third-party models. Audit it as a harness.

### Re-evaluate when

- A Jamba Large 2 appears on the API, or the `jamba-large` alias moves off the 1.7 snapshot.
- The Bedrock EOL (2026-11-26) approaches for any Bedrock-hosted Jamba workload.
- Moving between the Jamba chat API and Maestro — they are different architectures with different tool, MCP and validation surfaces.
- Changing the self-hosting stack, vLLM version, or model line, since the tool-call parser differs per model.
- A structured-output requirement hardens from "valid JSON" to "conforms to this schema."
- Output-size requirements grow past what a 4,096-token response can carry.
- A residency or retention obligation appears, since AI21 documents neither for its hosted API.
